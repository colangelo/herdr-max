Herdr uses several state paths for different situations.

## What survives

| Case | Processes keep running | Layout returns | Recent screen returns | Agent conversation resumes |
| --- | --- | --- | --- | --- |
| Detach and reattach | Yes | Yes | Yes, from the live terminal | Yes, because the process never stopped |
| Server restart | No | Yes | Only with pane screen history | Only with native agent session restore |
| Update without `--handoff` | Compatible servers keep running; restart-required servers may need stop/restart | Yes after restart | Only with pane screen history | Only with native agent session restore |
| Update with `--handoff` | Best effort for supported running servers | Yes | Yes, from the live terminal if handoff succeeds | Yes, because the process keeps running if handoff succeeds |

## Live persistence

Normal detach keeps the Herdr server running. Panes, shells, agents, servers, tests, and command processes keep running inside that server.

Detach the client with `ctrl+b q`. Reattach later:

```bash
herdr
```

This is the strongest persistence path because the original processes never stop.

## Snapshot restore

If the Herdr server stops and starts again, the original pane processes are gone. Herdr restores the saved session shape: workspaces, tabs, panes, cwd, layout, and focus.

Snapshot restore does not preserve running shells, servers, tests, or arbitrary processes. Panes that cannot use a stronger restore path come back as new shells in their saved directories.

If a saved directory is unavailable or the shell cannot start, the pane stays in the layout with an error instead of disappearing or moving to your home directory. Its saved directory and agent session reference remain intact. Fix the directory or shell configuration and restart the server to retry, or explicitly close the pane to remove it.

When saving, Herdr prefers the live shell's directory where the operating system exposes it, and retains the last confirmed directory after the shell exits. Shell-reported directories remain the fallback on other platforms.

If `session.json` cannot be read or parsed, or requires a newer Herdr version, Herdr logs why loading failed. Before saving or clearing the replacement session, it preserves the original bytes in `session-backups/` beside `session.json` and logs the recovery path as `persist.backup`. A file missing at startup is checked again before the first save or clear. These failed-load recovery copies are separate from normal snapshot history.

Herdr retains the three most recent recovery copies, pruning older copies only after a new copy is safely written. If preservation fails, autosave and shutdown leave the original untouched and log the failure; preservation is retried on the next save request. Copies are never restored automatically. To recover one, stop the affected server, copy the recovery file over its `session.json`, then restart. Recovery copies do not include pane screen history.

## Shutdown and snapshot recovery

On Linux systems with systemd-logind, Herdr listens for the host shutdown warning and requests a short delay while it saves and stops. This happens before logind proceeds with shutdown. The operating system limits the delay; Herdr does not block shutdown indefinitely. This protection is unavailable without logind and does not cover forced shutdown, power loss, or processes killed before the warning arrives.

Herdr also keeps up to 48 layout snapshots in `session-snapshots/` beside `session.json`, on all platforms. The first saved layout is copied immediately. Later saves or clears can add a snapshot of the previous saved layout, at most once every 15 minutes. Unchanged snapshots are not duplicated. The interval survives server restarts, so a burst of pane exits or restarts cannot rotate away all older layouts. Recent changes may not be in the recovery snapshots.

Normal pane closures still update `session.json`. There are no recovery prompts and no automatic restoration of older snapshots. To recover a layout:

1. Find the affected session directory with `herdr session list --json`.
2. Stop that server (`herdr server stop` for the default session, or `herdr session stop <name>` for a named session).
3. Keep a copy of its current `session.json`, then copy the chosen file from `session-snapshots/` over `session.json`. File modification times identify when snapshots were taken.
4. Start the session again.

Snapshots contain layout and agent session references, not running processes or pane screen history. Treat them as private session data. A snapshot-write failure is logged but does not prevent the primary session from saving.

## Pane screen history replay

Pane screen history restores recent terminal contents after a full server restart without restoring the old process.

Pane screen history is off by default because pane output can include secrets, tokens, prompts, and command output. Enable it in the config file:

```toml
[experimental]
pane_history = true
```

When enabled, Herdr stores saved pane history in `session-history.json` next to `session.json`. Treat the Herdr config/session directory like terminal history.

History is replayed only when it matches the exact saved layout. History from a different layout, including after manual snapshot recovery, is ignored. Older history files without layout verification are also ignored; newly saved history can be replayed on the next restart.

## Native agent session restore

Some agents can resume their own conversation sessions. Herdr can use official integration-reported session references to restart supported agent panes after a Herdr server restart.

Native agent session restore is enabled by default. Disable it with:

```toml
[session]
resume_agents_on_restore = false
```

Herdr resumes panes that reported a native session reference through a current official Herdr integration, and panes whose agent reported its own resume command. See [Add Herdr support to your agent](/docs/add-herdr-support/).

After a client attaches and provides terminal size and theme context, Herdr resumes eligible restored agent panes across workspaces and tabs without waiting for each pane to be focused.

Native session restore requires these Herdr integration versions or newer:

| Agent | Minimum Herdr integration version | Resume command |
| --- | --- | --- |
| Pi | `2` | `pi --session <path-or-id>` |
| Antigravity CLI | `1` | `agy --conversation <id>` |
| OMP | `3` | `omp --resume=<path-or-id>` |
| Claude Code | `6` | `claude --resume <id>` |
| Codex | `5` | `codex resume <id>` |
| Cursor Agent CLI | `1` | `cursor-agent --resume <id>` |
| Grok CLI | `2` | `grok --resume <id>` |
| GitHub Copilot CLI | `2` | `copilot --resume=<id>` |
| Devin CLI | `2` | `devin --resume <id>` |
| Droid | `2` | `droid --resume <id>` |
| Kimi Code CLI | `3` | `kimi --session <id>` |
| Qoder CLI | `2` | `qodercli --resume <id>` |
| Qwen Code | `1` | `qwen --resume <id>` |
| Letta Code | `1` | `letta --conversation <id>` or `letta --conversation default --agent <agent-id>` for `default:<agent-id>` |
| OpenCode | `5` | `opencode --session <id>` |
| Kilo Code CLI | `1` | `kilo --session <id>` |
| Hermes Agent | `2` | `hermes --resume <id>` |
| MastraCode | `1` | `mastracode --thread <id>` |

Run `herdr integration status` to check installed integration versions. Reinstall outdated integrations with `herdr integration install <agent>`.

Unsupported, missing, invalid, duplicated, or stale session references restore as normal shells in the saved pane directory.

If native agent session restore applies to a pane, Herdr resumes the agent session instead of replaying saved pane history for that pane.

## Live handoff

Live handoff is for update and remote attach flows that need to replace a running Herdr server. It asks the old server to transfer live panes to the new server, so pane processes can keep running across the server replacement.

Unlike snapshot restore, pane history replay, and native agent session restore, handoff tries to keep the current processes alive rather than reconstructing state after the old server stops.

A successful handoff preserves long-lived server-owned session state: pane PTYs and processes, agent identity and durable metadata, and plugin/session state needed by the replacement server. It does not preserve transient coordination across the replacement boundary. In-flight CLI or API requests, waits, subscription streams, client sockets, and pane-to-pane messages may be interrupted; clients should reconnect and retry them.

Updated Unix servers can send more than 64 panes in one handoff by transferring them in batches. The sending server must already contain this support: an older running server still enforces its 64-pane limit on the first upgrade. That limit may require a normal server restart, which ends pane processes. Batching does not change update installation order or remove other handoff compatibility requirements.

After a successful handoff, agent panes keep their pre-restart agent state: panes whose agents were working show the working indicator immediately, and the new server sweeps every pane in the background — nudging each agent to repaint and re-running detection — so agent states are re-verified across all workspaces within a few seconds without opening or clicking any pane.

Live handoff is experimental and opt-in:

```bash
herdr update --handoff
herdr --remote workbox --handoff
```

Plain `herdr update` installs the new client and keeps endpoint-generation-1 servers running. Plain `herdr --remote workbox` also keeps a compatible remote server running across version differences. A stop is required only for the one-time upgrade from a pre-generation-1 server; use `--handoff` when you explicitly want to replace a supported running server without losing its pane processes.

`herdr update --handoff` only applies to installs managed by Herdr's own updater. Homebrew, mise, and Nix installs are updated through their package managers, so `herdr update` is disabled there and cannot perform live handoff.

## Herdr Core panes: when the core stops or crashes

With `[experimental] runtime = "core"`, a pane's program runs in Herdr Core. The process that Activity Monitor shows as Herdr Core holds every core pane's program. When it quits or crashes, when the login session ends, or when a core restart loses programs, Herdr keeps each affected pane in its place. The pane shows that it is suspended. When the old program has ended, the pane starts again in place, and its agent resumes by its resume plan. Herdr shows one notice for each such event, with the number of panes.

Before a pane starts again, Herdr checks that the old program, and the agent that detection saw in the pane, have ended. If either still runs, the pane stays suspended and names the process. If Herdr cannot confirm that the program ended, the pane stays suspended until you run `herdr pane respawn` on it. Suspended panes start again in batches of eight, and the server keeps answering while they start.

If Herdr Core does not answer, the program keeps running. The pane keeps retrying, and after a minute it shows that Herdr Core is not answering. It attaches again as soon as the core answers. Herdr never starts a second copy of a program that may still run. A restored pane whose core does not answer shows `Waiting for Herdr Core (session <name>)` and starts nothing. It attaches when that core answers. To start it fresh instead, run `herdr pane respawn` on it.

Herdr counts a program as ended only when the process table says no such process runs. A lookup that fails counts as "may still run". The same holds for the agent that detection saw in a core pane, which Herdr saves with the pane. A restored pane also waits when a Herdr Core session that might hold its program does not answer. When more than one Herdr Core terminal is labelled for the pane, the pane names them and starts nothing. Close the ones that are not the pane's, and the pane attaches to the one that is left. A restored pane whose directory is gone attaches to its program if it still runs in Herdr Core, and otherwise starts nothing. In each case the pane keeps its link to the program across saves, restarts and live handoffs.

When Herdr Core may have started a program but did not answer, Herdr does not start the program on the PTY. It looks for the program in Herdr Core and attaches to it. While a suspended pane is starting again, `herdr pane respawn` on it is refused, and so is a live handoff. Try again a few seconds later.

When the core's socket has been missing or refusing connections for at least 3 seconds, Herdr starts its core again. This happens when the core server was killed. Its programs keep running, and the panes attach to them again. A planned core restart or update is shorter than 3 seconds, so Herdr does not start a core during one.

If you stop the core with `hc server stop`, the core panes wait for it, and Herdr does not start it. The panes start again after you run `hc server start`, or at the next Herdr start.

If Herdr Core ends panes three times within ten minutes, Herdr stops using it. Panes then start again on the PTY, new panes also use the PTY, and `herdr status server` shows `core: gave_up`. Run `herdr server reload-config` to use Herdr Core again. A live handoff or a server restart starts a new server, which uses Herdr Core again.

Quitting Herdr Core in Activity Monitor ends every core pane's program, so those panes start again. A macOS app started from a pane can appear in the Dock as "Running in Background". Do not stop such an entry: on macOS, stopping it can end every program in the same core.

### Which core session a pane runs in

Herdr Core keeps separate sessions, and each session holds its own programs. Herdr runs the core panes of each herdr session in one Herdr Core session:

| Herdr session | Herdr Core session |
|---|---|
| The default session (`herdr`) | `default` |
| A named session (`herdr --session work`) | `herdr-work` |

`default` is Herdr Core's own session, which Herdr Mobile and the Herdr apps show, so the default session's panes appear there. Other programs can also run terminals in `default`. Herdr marks its own terminals with the label `herdr.session=herdr` (`herdr.session=herdr-work` for a named session). Herdr never attaches to, lists, or ends a terminal without its label.

Earlier versions ran the default session's core panes in the Herdr Core session `herdr`. After an update, a restart, or a live handoff, Herdr finds those panes in `herdr` and attaches to them again. New panes start in `default`. Herdr does not start the `herdr` session.

If the Herdr Core in `default` was started over SSH, Herdr shows the notice `Herdr Core in session default was started over SSH; restart it from a desktop terminal`. Herdr does not restart that core, because other programs share it.

### Rolling back with core panes open

Rolling back to the previous version (the one that reads both `default` and `herdr`) is safe: it attaches to the panes in both sessions again. An older version, beta 202 or earlier, looks only in `herdr`. It starts each pane from `default` again as a new program and leaves the old program running. Before such a rollback, close the core panes, or list their terminals:

```sh
HC_SESSION=default hc ls --label herdr.session=herdr
HC_SESSION=herdr hc ls --label herdr.session=herdr
```

When you return to this version, a notice names the terminals that were left running without a pane. Herdr leaves them running. End one with `HC_SESSION=default hc kill <address>`.

### Keeping a pane on the PTY

Some programs must not move to Herdr Core. On macOS, a privacy grant such as Screen Recording or Accessibility belongs to the process that asked for it, and a program in Herdr Core asks as Herdr Core. To keep such panes on the PTY, list their names in `[experimental] core_pty_panes`:

```toml
[experimental]
runtime = "core"
core_pty_panes = ["*-hlp"]
```

Each entry is a pattern: `*` matches any run of characters, and `?` matches one character. Matching is case-sensitive. A pattern matches a pane's stable name. The stable name is the `--name` that the pane's agent was started with, for example `claude --name manager-lab-hlp`. When the agent was started without one, it is the agent name set with `herdr agent rename`. A terminal title, or a name that the agent reports about itself, is never a stable name. A pane without a stable name always uses `runtime`.

A matching pane starts on the PTY when it is created with a command that names its agent, when it is restored, when it starts again after a suspension, and when it is respawned. A new pane that starts as a shell has no name yet, so it uses `runtime`. Name it, then run `herdr pane respawn` on it. A pane that already runs in Herdr Core stays there after you add a pattern. Run `herdr pane respawn` on it to move it to the PTY. `herdr server reload-config` applies changes to the list to the next pane that starts.

### Moving idle panes onto Herdr Core

Panes that already run on the PTY, or in the older Herdr Core session `herdr`, stay where they are. `herdr pane respawn <pane_id> --if-idle` moves one onto the session where new panes start, only when nothing happens in it. The server checks the pane and kills its old program in one step, and it starts the replacement only after Herdr Core confirms that the old program ended.

The server refuses a move, and changes nothing, for each of these reasons:

| Refusal | Meaning |
|---|---|
| `already_on_primary` | The pane already runs where new panes start. |
| `excluded` | The pane matches `core_pty_panes`. |
| `core_off` | `runtime` is not `core`, or Herdr gave up on Herdr Core. |
| `not_movable` | The pane is suspended, waits for Herdr Core, is starting again, is an overlay, or a worktree removal is stopping it. |
| `recent_input` | Input reached the pane in the last 60 seconds. This includes keys, text from the API, a message still waiting to be submitted, and a note sent to its agent. |
| `unsupported_agent` | Herdr cannot tell when this agent is idle. Today only Claude Code can move. |
| `agent_busy` | The agent has not been idle for 60 seconds. A Claude Code subagent keeps it busy. |
| `background_work` | The agent shows background work: shells, monitors, background agents, or MCP tasks. |
| `draft_in_box` | The agent's input box holds text, or Herdr cannot see it. |
| `no_resume_plan` | Herdr has no command to resume the agent's session. |
| `foreign_process` | Something other than the agent runs in the pane, for example a job that a shell escape left running. |
| `shell_busy` | The shell is not at its prompt, or runs a job. |
| `shell_recent` | Input reached the shell pane in the last 10 minutes. |
| `core_unreachable` | Herdr Core answered that the old program still runs after the kill. The pane keeps its program. |

Before a moved agent's pane is killed, Herdr sends the agent SIGTERM, so it saves its conversation, and kills it if it has not exited after 3 seconds. Once Herdr has sent a signal, the move does not close the pane or leave it as it was. If the old program still runs, or Herdr Core does not answer, the move still answers `moved`, and the pane waits, suspended, until the old program is gone. Then it starts again in place, as after a lost session.

A moved agent starts again through its resume command, the same command that `pane respawn --resume` types, so it keeps its conversation, name, model, effort, and permission mode. A moved shell starts again in the same directory with the pane's scrollback. It loses its process state: shell variables, jobs, and the history in its memory. That is why a shell must be quiet for 10 minutes before it moves.

`scripts/core_move_idle_panes.sh` moves every pane that can move, one at a time. Without `--move`, it lists the panes and the reason the server gives for each. With `--move`, it moves one pane first, checks it, then moves the rest. It stops at the first pane whose check fails, whose move answers anything but `moved`, or that is gone or holds another agent than the one it listed. Before an agent moves, `agent-bell` must report no queued message for its session. `--exclude <glob>` skips more names for that run. Use `--herdr herdr-beta` to drive a beta build.

## macOS: after a logout

On macOS, a server that Herdr starts in the background (the usual `herdr` launch) runs in your account's per-user context, which survives logging out. A server started another way, or carried forward by live handoffs from such a server, can run in a login session's context instead. When that login ends, for example after a crash logs you out, every pane the server starts can no longer resolve host names, read the keychain, or use `launchctl`.

`herdr status server` shows which context the server runs in:

- `macos_services: user context, reachable`: survives a logout.
- `session context`: tied to a login session, so it breaks at the next logout.
- `unreachable`: it already broke. Every attached window then shows a warning line.

To recover, run this in a terminal that still works, such as Terminal.app:

```bash
herdr server restart
```

It asks first, because every pane's running process ends. Workspaces, tabs, panes, todos and agent sessions come back as after any restart, and open windows reattach on their own. Pass `--yes` to skip the question. It refuses to run in a terminal that has lost its session too, because a server started from there would be just as broken.

A live handoff keeps the old server's context. To move a server from a session context to the per-user one without ending its panes, hand it off with `--user-context` before the next logout:

```bash
herdr server live-handoff --user-context
```

Panes that already lost their session stay broken after a handoff. Only a restart replaces them.
