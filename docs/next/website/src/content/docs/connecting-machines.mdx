title: Connecting machines
description: Work across Local and saved SSH machines in one Herdr window, with shared agent navigation and independent reconnects.
---

Keep your local work and remote agents in one Herdr window. Save an SSH machine once, then switch between its workspaces and Local without opening another client. The agent list includes connected machines, so you can see where work is running and which agent needs an answer.

Each machine keeps its own Herdr server, sessions, and running processes. A lost connection to one machine does not disconnect the others.

Herdr requests SSH compression to reduce screen-update traffic on limited connections. This works with older compatible Herdr servers and does not change how typing or other input is delivered. Herdr's `-C` option overrides `Compression no` in your SSH config. If SSH reuses an existing connection through an external ControlMaster, that connection keeps its original compression setting.

### Recovering SSH authentication

On Linux and macOS clients, when `remote.manage_ssh_config=true`, Herdr shares an approved OpenSSH connection across machine add, the sidebar, and saved-machine API commands. Run `herdr machine status [<label-or-id>] [--json]` for fresh, noninteractive checks. **Reachable** means the remote Herdr server is available now, not that every open TUI is connected. Run `herdr machine reconnect <label-or-id>` in a terminal to complete native SSH authentication and verify the saved machine. It does not install or update Herdr. Open clients recheck failed connections within 30 seconds; no restart is needed. Clicking **`! auth`**, **`! error`**, or a reconnecting status retries the connection; if it fails, a notice shows the latest error and relevant CLI command. It never opens a credential popup.

The shared connection uses `ControlPersist 600` (10 minutes of idle time); this is not MFA validity. Active connections can remain open, while corporate policy, the SSH server, or the network may end them sooner. Local Windows recovery is not supported yet. For unmanaged SSH connections, authentication remains your responsibility: running `ssh` by itself does not grant Herdr approval unless it uses the shared ControlPath. Host-key checking is unchanged; an unknown or changed host key remains **Attention**.

Saved TUI connections check whether an existing shared SSH connection can open a new channel. CLI status and API commands check only after an initial read-only connection failure. If reuse fails while a fresh connection to the same host succeeds, Herdr retires the old connection from reuse and reconnects. Existing channels stay open. A fresh connection that needs authentication or rejects the host key does not trigger this recovery. API commands retry connection setup at most once and never repeat a request that may already have changed remote state.

## Before you connect

You need normal SSH access to the remote machine. Verify it first:

```bash
ssh workbox
```

`workbox` can be a host from your SSH config. You can also use a target such as `ssh://you@server:2222`.

Multi-machine connections support Linux, macOS, and Windows clients connecting to Linux or macOS servers on x86_64 or aarch64, or Windows servers on x86_64. Interactive setup can install or update the complete remote package after confirmation; background reconnects only discover installed packages. See [Remote attach over SSH](/docs/persistence-remote/#remote-attach-over-ssh) for SSH configuration, authentication, and custom binaries.

## Add a machine

Run setup in an interactive terminal so Herdr can ask before installing or replacing anything:

```bash
herdr machine add workbox
```

In an interactive terminal, Herdr discovers running sessions: it selects the only running session, or lets you choose with Up/Down and Enter when several are running. Esc or Ctrl+C cancels. If a successful query finds no running sessions, setup uses `default`. If no Herdr installation is found, setup offers to install it for `default`. If an installed binary cannot report its sessions, setup reports the error; pass `--remote-session <name>` to select a session explicitly.

The sidebar shows the default session as `workbox`, the SSH host without any `user@` prefix. Add `--label "Build machine"` to choose a different name. A machine profile targets one remote session; it does not combine every session on the host. Non-interactive commands use `default` unless `--remote-session` is supplied.

To skip discovery and use a specific session, add `--remote-session`:

```bash
herdr machine add workbox --remote-session agents
```

Without `--label`, this machine shows as `workbox/agents`. If the default name is already taken, `machine add` asks you to pass `--label`.

On Windows servers, setup also checks executables used by Herdr processes owned by the SSH user. It validates their capabilities before reuse, so a compatible running build can be used even when SSH's `PATH` points to an older installation.

Herdr checks both the installed binary and the running server. It starts the requested background server before saving the profile. Compatible client and server versions do not have to match. Missing or incompatible installations go through an approval-based setup. When the running server needs replacement, setup asks before stopping it and its pane processes, then starts the compatible server. The default answer is No. If installation and replacement are both needed, one confirmation covers them. `machine add` does not use experimental live handoff. Cancelling or failing setup leaves the profile unsaved.

Run `herdr` to open the UI. If a local client is already open, added and enabled machines normally appear within a second and connect in the background without changing your selection. An in-progress machine switch finishes before profile changes are applied. The remote server keeps running after setup exits.

## Switch between machines

Choose a machine or one of its workspaces in the sidebar. The selected machine receives your pane input and terminal size, and supplies the visible terminal content and graphics. Other connected machines keep updating their workspace information, agent states, and notifications without streaming their pane screens.

Click the arrow beside any machine to collapse or expand its workspace list without switching away from your current workspace. This also works while that machine is reconnecting.

For keyboard navigation, press `prefix+w`, then use the workspace navigation keys (Up/Down by default) to highlight workspaces across connected machines in sidebar order. Enter activates the highlighted workspace; Esc or the prefix key cancels without switching. Compact and expanded sidebars reveal the highlighted row, including under a collapsed machine. On desktop, navigation wraps at the ends; the mobile switcher stops at the first or last workspace. Disconnected machines are skipped.

When highlighting a workspace on another machine, press Enter before using other keyboard actions. This prevents pane, tab, workspace, or custom-command shortcuts from acting on the current machine by mistake. Clicking cancels a remote desktop keyboard preview. Expanded sidebars respect each machine's collapsed worktree groups.

Local opens immediately on startup without waiting for SSH connections. Selecting Local also cancels an unfinished remote switch without waiting for the remote machine to reply. If Local itself is reconnecting, your selection resumes when it is ready. Local accepts input once its fresh screen and terminal settings are ready. A stalled machine cannot hold up another machine's input. Multiple Herdr clients can also view different tabs on the same server independently; see [Client and server](/docs/concepts/#client-and-server) for shared-tab sizing.

When a connection is lost, the last workspace and agent state remains visible but dimmed. That is cached information, not live state. Input and navigation into those cached panes stay disabled until a fresh connection and matching screen arrive. Reconnecting never takes selection away from the machine you are using.

## Rename, disable, or remove

Read profile IDs from the list rather than deriving them from labels or hostnames:

```bash
herdr machine list
herdr machine rename <profile-id> --label "New name"
herdr machine disable <profile-id>
herdr machine enable <profile-id>
herdr machine remove <profile-id>
```

For scripts, add `--json` to `machine list`.

Renaming changes the displayed label without reconnecting. Disabling keeps the profile for later; removing forgets it. Both disconnect only that machine from the client and leave its remote sessions and agents running, even if the host is unreachable.

Removing or disabling the machine you are viewing returns you to Local. If Local is unavailable, Herdr shows that and retries its connection instead of selecting a different remote machine. With enabled saved machines, the client can remain usable even if Local fails or restarts.

## Connection problems

- **Reconnecting:** Herdr retries automatically after a network interruption, sleep, or SSH failure. Repeated failures increase the delay up to two minutes; brief successful connections do not reset it. A connection must remain healthy for a minute before the next interruption gets a fast retry. SSH connections are checked for application-level activity and probed when quiet, so a broken connection does not stay Online indefinitely. Local detects native connection closure or failure instead of using remote health probes.
- **Attention:** The target needs an action such as authentication, host-key approval, or a compatible server. Other machines remain usable. **`! auth`** means authentication failed; **`! error`** indicates another issue. Click the badge to retry; if it fails, a notice shows the fresh error and a CLI command. In a collapsed sidebar, either appears as `!`.
- **Saved-machine file error:** An unreadable or invalid catalog leaves current connections unchanged. Herdr shows a notice and automatically retries reading it.

When both installations support bridge idle cleanup, saved-machine connections to Linux and macOS also close their remote bridge after a minute without traffic in either direction. Sleep counts toward that deadline, which is checked when the host wakes. Quiet healthy connections exchange health checks; watching continuous output does not require typing. Cleanup leaves the remote Herdr server, sessions, and pane processes running. Older installations remain compatible without this optional cleanup.

Background connections never answer prompts or install, update, restart, or hand off a server. For non-authentication Attention, run the standalone setup command shown by Herdr in an interactive terminal, for example:

```bash
herdr --remote workbox
```

Use your profile's target. If you chose a named session when adding it, include the optional `--session <name>` here too. Follow the requested setup prompts; open clients retry automatically. `machine reconnect` does not install or update Herdr. Do not stop a running server merely because its version differs from the client.

If authentication fails, check ordinary SSH first. For a passphrase-protected key, load it with `ssh-add` before starting Herdr's non-interactive background connections.

For Git authentication or SSH signing inside remote panes, enable `ForwardAgent yes` for the trusted host in your SSH config. Herdr does not enable forwarding for you. When a session starts with an agent, updated Linux and macOS servers give panes a stable agent address, so existing and new panes can use the forwarded agent after `--remote` or a saved machine reconnects. A working inherited agent or earlier connection keeps priority over later clients and temporary setup checks; if it disappears, another live attachment can supply the agent.

This requires an updated remote server, not just an updated local client. Local sessions started without an agent leave `SSH_AUTH_SOCK` alone. Panes created before the server update, or before an agent was first supplied to the session, keep their original environment and need to be recreated once to inherit the stable address. Older compatible servers and connections without agent forwarding can still attach normally.

## Settings and automation

The UI uses the client's local theme, sidebar settings, and keybindings by default. Custom commands and plugins advertised by the selected server still run there. Herdr does not copy local command plugins, configuration, executables, or secrets onto SSH hosts. Missing remote commands fail visibly. Use the UI's `reload config` action after editing client settings; see [Configuration](/docs/configuration/#reload-config).

Default agent rows show a `machine` token when multiple machines are present. Existing custom rows are preserved; add `machine` explicitly if you want that label in your layout. [Sidebar row layouts](/docs/configuration/#sidebar-row-layouts) also support conditional colors for machine labels.

Workspace, tab, pane IDs, and agent names are scoped to one server. Two machines may both contain `w1:p1` or an agent named `reviewer`. Selecting a machine in the UI does not retarget CLI commands running in an existing pane: they still use that pane's inherited session and socket. For remote automation, use `herdr --machine <label-or-id> agent list`, then pass the same prefix when controlling those remote IDs. The CLI uses the saved profile's SSH target and session directly; it does not need an open TUI. Without `--machine`, existing session/socket routing is unchanged. See [CLI reference](/docs/cli-reference/#saved-ssh-machines) for supported commands, update requirements, and remote path rules.

## Herdr Core machines

With `[experimental] runtime = "core"`, your Herdr Core can link to the Herdr Core of another Mac or Linux host, as a **core machine**. Panes can then run their programs there (see [Panes on a Herdr Core machine](#panes-on-a-herdr-core-machine)), and `herdr --machine <name>` reaches that host's own Herdr through the same link. Saved SSH machines, `herdr --remote` and their `--machine` stay as they are, beside core machines: they are the fallback.

Add a core machine from a terminal, as a person:

```bash
herdr machine add --core ac@workbox
herdr machine add --core ac@workbox --name workbox --remote-session default
```

`--name` is the machine's name in Herdr Core (the SSH host by default), the first part of its terminals' addresses (`workbox/t7`). `--remote-session` is the Herdr Core session there (`default` by default). `--ssh-config <file>` reads that SSH config file instead of Herdr's managed one. Run it in a terminal: Herdr Core may ask there before it copies itself to the host, and SSH may prompt. Without a terminal, `machine add --core` refuses and prints the command for a person to run. Herdr never installs or updates Herdr Core on the other host.

Herdr Core reaches the machine through `herdr core-link <name>`, which runs OpenSSH with no shared connection: every connection is a fresh SSH login, which can ask for Touch ID (1Password's SSH agent) or a Tailscale SSH check. It does not start Herdr Core on the other host: when Herdr Core is not running there, the link stays down until Herdr there starts it. (On a Linux host whose `nc` has no `-U`, the check falls back to the socket file, so after a crash there a connection can start Herdr Core under the SSH login.)

### Dormancy

A core machine's link is up only while someone uses it. Each of these keeps it for a while:

- Input (a key, text, a paste, a click, a drag or a scroll; moving the pointer is not input) in a Herdr client on this Mac: 10 minutes after the last one. Starting a client is not input. Such input allows every core machine this session's Herdr Core added and lists, because it means a person is at this Mac and can answer a Touch ID prompt; it wakes none by itself (see below). A window of the old SSH remote (`herdr --remote <host>`) writes no lease; a view's window (`herdr --remote core:<machine>`) does. A client whose environment sets `HERDR_NO_MACHINE_LEASES` writes none, and `herdr machine status` says so.
- `herdr machine add --core` and `herdr machine login`: 30 minutes.
- `herdr machine wake <name> [--for <90s|30m|2h>]`: 30 minutes by default, at most 12 hours.
- A `herdr --machine <name>` call: while it runs. Its lease keeps a link that is up, and never connects one by itself (only `--dial` connects, once). It lasts a minute past its last renewal, renewed every 30 seconds while the call runs, so a call that is killed outright stops keeping the link within a minute; Ctrl-C (SIGINT), SIGTERM and SIGHUP remove it at once.

After that the link closes and nothing goes to the machine: no polling, no keepalives, no reconnects. A server restart, a live handoff or a start of Herdr Core does not wake it. The first input in a pane on that machine or in a view of it, a `machine wake` or a `--machine --dial` call wakes that machine at once. Input in a pane of this Mac wakes no machine; while its lease is in force, Herdr Core's own retry (every 30 seconds by then) may connect one. While a machine is dormant, Herdr Core leaves its terminals out of its lists.

### Status and the gate

```bash
herdr machine status --core [<name>] [--json]
```

For each core machine: `state` (Herdr Core's: `connected`, `connecting`, `unreachable`, `needs_login`), `gate`, the leases that keep the link and when they end (`leases`), the last connection (`last_dial`), and `far_herdr`, the other host's Herdr that `--machine` found over the current link. `gate` says whether a connection may be made now:

| `gate` | Meaning | What reopens it |
|---|---|---|
| `open` | A connection may be made. | — |
| `dormant` | Nothing keeps the link: no recent input, wake or call. | Input, `herdr machine wake <name>`, `herdr --machine <name> --dial`. |
| `needs_check` | A Tailscale SSH check asked for a sign-in in the browser. | A person runs `herdr machine login <name>` in a terminal. |
| `auth_stalled` | No answer 15 s after SSH started: a prompt nobody answered, such as Touch ID. | `herdr machine login <name>`. |
| `auth_failed` | Authentication or the host key failed. | `herdr machine login <name>`. |
| `far_core_down` | Herdr Core does not run on the other host. Reopens by itself after 5 minutes. | Start Herdr there, then `herdr machine wake <name>`. |
| `retry_spent` | Two connections in a row ended without a link. | Input, `machine wake`, `machine login` or `--machine --dial`. |

`herdr machine login <name>` runs SSH in your terminal, so a check, a Touch ID prompt or a host key is answered there, then reopens the gate and connects. A prompt nobody answers closes the gate in 15 s, so no unattended run waits on it or repeats it. Remove a core machine with `herdr machine rm --core <name>`; its programs there keep running.

### `--machine` to a core machine

`herdr --machine <name> <command>` reaches a core machine when no saved SSH machine has that label or ID (a saved machine with the same name wins). The request goes through Herdr Core's link to the other host's own Herdr API, so the reply is that Herdr's own, with its pane IDs, as with a saved SSH machine. The commands are the same as for [saved SSH machines](/docs/cli-reference/#saved-ssh-machines).

```bash
herdr --machine workbox pane list
herdr --machine workbox --dial agent list
```

- **Connected:** the call rides the open link; no new SSH login. When the link drops during the call, the call fails and the link is not connected again on its account.
- **Not connected:** the call is refused with exit code 75, `workbox is dormant; reaching it opens ssh (a Touch ID or Tailscale check can prompt). Announce it, then rerun with --dial, or run herdr machine wake workbox.` Nothing is written and nothing connects.
- **`--dial`:** connects once, then sends the call as on a connected machine. Before it connects it prints one line on stderr, `herdr: --dial: opening ssh to workbox now; a Touch ID or Tailscale check can prompt on this Mac`. Pass it on each call that may connect; no setting turns it on. One `--dial` gives one connection: if Herdr Core retries or the link drops, the call does not connect again. It is refused when the gate is `needs_check`, `auth_stalled` or `auth_failed` (run `herdr machine login`), or when Herdr Core was found not running there in the last 5 minutes (`far_core_down`, or `retry_spent` after a retry that found the same).

The other host's Herdr session is the one whose Herdr Core session the machine was added with: `default` reaches its default session, `herdr-<name>` its session `<name>`. The Herdr found there must say that its session runs in that Herdr Core session (an older Herdr that does not say is taken for a release build, which never uses a debug build's `herdrdev` sessions); otherwise the call is refused before any request. Herdr finds its Herdr once per connection, and again after 5 minutes or after any request through it fails (the name this Herdr runs as, then `herdr`, on its `PATH` and in `~/.local/bin`, `/opt/homebrew/bin` and `/usr/local/bin`). That Herdr must be one that forwards a single request (`herdr remote-api-bridge --request`, this version or later); an older one is passed over, and with none the call is refused, saying that the request was not sent. The machine must be the one `herdr machine add --core` added: if Herdr Core lists another machine under that name (one added with `hc machine add` directly), the call is refused before anything is sent.

A request is sent once and never repeated after a failure. Any failure after the request was sent (a dropped link, no answer, a timeout, an error exit of the other host's Herdr, a reply that is empty or not one whole reply to that request) says that it may have run there. A reply cut at 8 MiB, or one that timed out, is an error (exit code 1) and none of it is printed. A request over the Herdr API's line limit (1 MiB) is refused before it is sent. Text from the other host in a message or in `herdr --machine <name> status` (its error output, its version) is shown with its terminal control characters escaped, as `\x1b`; JSON output is unchanged. Herdr Core runs a program on a machine for 600 seconds at most, so a wait with no `--timeout` (such as `pane wait-output`) ends after 600 seconds with a timeout, and one with a `--timeout` over 590000 ms is refused before it is sent: for a longer wait, run it again in a loop with `--timeout 590000` or less, or use a saved SSH machine. Herdr's integration variables (`HERDR_ENV`, `HERDR_PANE_ID`, `HERDR_SOCKET_PATH` and the rest) are removed from what the other host's Herdr gets, even when its Herdr Core has them.

### Announce a connection first

Agents: a connection to a core machine can prompt on this Mac (Touch ID) or in the browser (a Tailscale SSH check). Before you pass `--dial` or run `herdr machine wake`, say so to the person, as for adding a machine. A `--machine` call on a connected machine opens no SSH and needs no announcement; one on a dormant machine is refused and connects nothing. A person at the terminal needs none.

Herdr Core's own commands do not wake a dormant machine: `hc exec --on` and `hc run --on` fail at once, and `hc machine connect` fails at Herdr's link unless something keeps the link. Use `herdr --machine <name>` or `herdr machine wake <name>`, which follow the rules above.

## Panes on a Herdr Core machine

With `[experimental] runtime = "core"`, a pane can run its program on another Mac or Linux host that your Herdr Core reaches as a [core machine](#herdr-core-machines) (`herdr machine add --core <target>`). The pane stays in this Herdr window, with an ID from this server. Only its program runs on the other host:

```bash
herdr pane split --direction right --on ac-mbm5
herdr tab create --on ac-mbm5 --cwd /Users/you/project
herdr workspace create --on ac-mbm5 --label mbm5
```

`--on` names the machine as Herdr Core lists it. The new pane runs the machine's own login shell, or the command a request gives, found on that machine's `PATH`. `--cwd` is a folder on that machine; without it, the pane starts in the folder Herdr Core gives it there. None of this Mac's folders, shell or environment variables go along, only the terminal's `TERM` and `COLORTERM` and the variables you pass with `--env` (less Herdr Core's own `HC_*` variables, which would point an `hc` there at another session). `--on` needs a server that advertises the `spawn_on_machine` capability; against an older server the CLI refuses and starts no pane, because that server would start the pane on its own host.

`herdr pane list --json` gives such a pane `machine` (`"ac-mbm5"`) and `core_address` (`"ac-mbm5/t7"`, the terminal as your Herdr Core names it). Panes on this Mac have no `machine` field. Every other field keeps its meaning.

When the machine is not connected, typed input is not sent and the first key starts a reconnect, while a lease allows the machine's link (someone typed or clicked in a Herdr window in the last 10 minutes; starting Herdr alone is not use, and a window's lease ends when the window closes). Input through the API, such as `herdr pane send-text`, writes no lease, so it never wakes a dormant machine. After a restart, a live handoff, or a link loss, the pane keeps its place and waits: `core_waiting` is `true`, with `core_waiting_cause` set to `machine_dormant` (no one used the machine for 10 minutes; press a key in the pane) or `machine_unreachable` (its link is down). It attaches to the same program on the machine once the machine is connected again. It is never started again on this Mac. A restart or handoff does not wake a dormant machine. A stop or restart of this Mac's Herdr Core makes the pane wait the same way.

Such a pane ends only when Herdr Core reports its program there as finished. Herdr Core leaves the terminals of a machine that is not connected out of its answers, and can list the machine as connected before it lists all its terminals again, so a terminal it does not list is never taken as an end. While the machine is connected but its terminal is not listed (or is listed for another pane), the pane waits with `core_waiting_cause` set to `machine_terminal_missing` and asks again every 5 seconds; nothing starts, here or on the machine. When the program exits while the pane is attached, the pane closes as any pane does when its program exits. When Herdr Core reports it finished while the pane waits, the pane keeps its place with `core_waiting_cause` set to `machine_ended` and says so. It keeps that state through restarts and is never started again, here or on the machine; close it, or open a new pane with `--on`.

Herdr never ends a program on a machine by itself: only closing its pane does. A program that ended, a lost stream, a failed attach, a stop of this Mac's Herdr Core, a worktree removal, and a stop of this server (a logout included) send no kill to the machine; after a stop, the saved pane attaches to the program again when the server starts. Closing a pane that waits for its machine, or whose program ended, sends nothing to the machine, and the pane says so: a program still running there shows as an orphan of this session once the machine is connected again.

Each pane on a machine carries the label of the run that started it, `herdr.launch`, and saves it with its terminal. If the other host's Herdr Core loses its state and gives the address to another terminal, even one with this pane's other labels, the pane does not attach to it, does not take its end for its own, and closing the pane does not kill it: the pane waits as for a terminal that is not listed.

`herdr pane respawn` (and `--resume`) refuses a pane on a machine with `pane_on_machine`, whether it runs, waits or ended there, because a respawn starts its program on this Mac. `herdr pane respawn --if-idle` refuses it with `on_machine`, and a suspended pane on a machine is never started again here: it waits for its machine.

A saved pane on a machine records its terminal and folder in a field of their own, `core_machine_terminal`, and `/dev/null/herdr-pane-on-a-core-machine` as its `cwd`, a folder no host has. A Herdr build from before panes on machines reads no terminal for such a pane, so it shows the pane as "Saved directory is unavailable" and never starts it, or attaches another terminal to it, on this Mac; it also drops the pane's link from its next save, so after a downgrade the pane's program on the machine runs on without a pane. Close or move panes on a machine before you go back to such a build.

A pane on a machine lacks what Herdr learns from this Mac's processes:

- **No Herdr hooks or integration variables.** Its program gets no `HERDR_ENV`, `HERDR_PANE_ID`, `HERDR_TAB_ID`, `HERDR_WORKSPACE_ID`, `HERDR_SOCKET_PATH` or `HERDR_CLIENT_SOCKET_PATH`, even when the far Herdr Core has them. An agent hook there that runs `herdr pane report-agent` finds no pane and reports nothing. Agent status comes from the agent's own terminal status reports (Claude Code and Codex send them) and from screen detection, so hook-only facts, such as the agent session, are missing.
- **No process facts.** Its process ID belongs to the other host, so the process list, foreground directory, and process-based agent detection give nothing for it. `agent start` cannot start an agent in such a pane; start the agent as the pane's command instead.
- **Close ends the program only.** Closing the pane ends its terminal on the machine. Jobs the program left running in the background there keep running, as Herdr Core's own kill leaves them; Herdr does not sweep that host's processes.
- **Its output is the other host's.** Kitty graphics show only when the image data is in the output itself; a file, temporary-file or shared-memory image names something on the other host and is not loaded here. A program there cannot set this Mac's clipboard (OSC 52); copying text you select still works. The folder it reports (OSC 7) is a folder on that host: Herdr saves it with the pane, and never takes it for a folder of this Mac, so a new pane split from it, the workspace's name and its Git status come from this Mac's own folders.

The other host's own Herdr never claims, lists, or ends these panes, and this Herdr never adopts that host's own panes.

To start a pane on a machine from the TUI, right-click a pane: the menu lists **Split right on** each core machine Herdr added, with its gate (`open`, `dormant`, or why it is closed). The menu offers machines only while the server advertises `spawn_on_machine`, and only for this Mac's own server, not for another machine you are viewing.

## View another Mac's Herdr through Herdr Core

`herdr --remote core:<machine>` shows the other Mac's own Herdr workspaces, tabs and panes through the Herdr Core machine link, instead of Herdr's own SSH. Each core machine Herdr added also appears as a machine in the sidebar, also when the machine is added, or this session's Herdr Core starts, after the window opened (a window looks every 30 seconds). Both start a view server for that machine on this Mac when none runs; it stops 10 minutes after its last window closes. A window of a newer Herdr build restarts a view of an older one; a view keeps nothing, so nothing is lost. A window of an older build uses a newer view as it is: after going back to an older Herdr, run `herdr server --view <machine> --restart` (or wait until the view stops), which ends the running view of any build and starts one of yours. A `--remote core:` window on a view that restarts closes with it.

The view follows the other Herdr's layout as it publishes it to its Herdr Core (`[experimental] core_spaces_doc = true` there): a new tab, a split, or a rename there shows here within a second or two. Typing, pasting and clicking reach the other Mac's programs, but the view never takes their size: it shows each pane at the size the other Mac gives it, cropped or padded, with that size in the pane border when it differs. Programs there get no focus reports from the view, and an agent's `hc send` to such a terminal cannot see that you are typing in the view. Herdr's own agent status there shows here as that Herdr reports it to Herdr Core; the view runs no detection of its own. When the link does not take automatic input, the view is read-only and says so in the pane border.

A view shows the other Mac's Herdr and passes on what you type. A view's window offers only what a view does: focusing, zooming, scrolling, copying and selecting, clearing its own copy of a screen, marking things seen, and closing. A few actions are done by the other Mac's Herdr, which the view asks through the Herdr Core link: a new tab, a split, closing a pane, and renaming a workspace, tab or pane. Names go there as data, never as a command line. The other Mac's Herdr starts the new tab's or split's shell there, and the view shows it on the next layout it publishes; the view's focus stays where it was. On a dormant machine such an action is refused and sends nothing: press a key in one of its panes to wake it, then do it again. The action itself connects nothing, but its keys are input in Herdr like any other: while that input's lease is in force, Herdr Core's own retry may connect the machine. A Herdr there too old for the action says so, and the view stays connected. Everything else is refused, with the reason, before it runs: the rest of the other Mac's layout (new workspaces, moving, swapping, resizing, pinning, synchronized input; use the other Mac's Herdr, or `--on`), and whatever would run or write on this Mac: custom commands, plugin actions, every worktree action, opening or resolving a link, editing the scrollback, todos, tasks, integrations, a clipboard image paste, release notes and announcements, and sending to a session from the command palette (it offers no send in a view, so no note through this Mac's `note_command`). The other Mac's folders stay its own: the tab bar's status commands do not run in a view and no Git runs here for them. Closing a pane in the view (`prefix+x` or the pane menu) closes that pane on the other Mac and ends its program there, as closing it in the other Mac's Herdr would. Closing a tab or a workspace in the view, or closing the view, only stops showing it: its programs and panes stay on the other Mac. An action on a pane reaches only the program you see: it is refused on a pane whose border says it shows another terminal now (click the pane first), on a pane that is still attaching, on a pane the other Herdr has not numbered, and when another program runs there now (for example after Herdr Core restarted on the other Mac). The other Mac's Herdr checks again, in the same step as the action, that the pane still runs that program, and refuses it otherwise, so a pane that changed between the view's check and the action is not hit: closing, splitting and renaming a pane from a view needs a Herdr there that makes this check, and an older one refuses with a notice to update Herdr there. An action on a pane goes only for a pane of the tab your window shows, and a second action on a machine while one runs is refused, not queued: do it again when the first ends. When the other Mac's Herdr asks you to confirm a close (open todos), your confirmation is good for that one close of that pane and program, for 2 minutes. Closing the last pane of a workspace is not done from a view, because the other Mac's Herdr would close the workspace with it (and for a worktree group's parent, the whole group): close it there. The other Mac's Herdr refuses it too. Panes that do not run in Herdr Core there are not shown.

What you type goes to the terminal you see. When the other Mac's layout puts another terminal under a pane, or the terminal at its address is another program (after the other Mac's Herdr Core lost its state), the pane takes no input until you click it or move the focus to it, and its border says `another terminal now: click to type`; keys typed for the old terminal reach neither.

A view builds a pane's grid only for a size up to 1000 columns, 1000 rows and 300 000 cells. A pane the other Mac gives a larger size does not attach and says why; a later larger size is ignored and the pane keeps its last one. A view reads the other Mac's layout at most twice a second, and attaches at most 8 terminals at once.

A view never answers for the other Mac's programs: their terminal queries (device attributes, cursor position, colors, the keyboard protocol) are answered by the other Mac's own Herdr, and the view sends nothing for them. Its output is the other host's, as for a pane on a machine: Kitty graphics only inline, no clipboard writes (OSC 52), including from the history replayed when the view attaches, and no folder of this Mac.

Opening Herdr, opening a view or attaching a window to one never wakes a dormant machine. A view of a dormant machine says so and wakes it with your next key or click in Herdr, as other panes on a machine do. It reads the machine's state only while a window is attached and the machine is away or you type, so an idle view sends nothing.

The saved machines of [Add a machine](#add-a-machine) keep working unchanged. When one is the same Mac as a core machine, both are shown, and the client says so once. `[remote] prefer` decides which path `herdr --machine <name>` takes when both share the name: `ssh` (the saved machine, the default) or `core`. A name that only a core machine has always takes the Herdr Core link.

## Updates and saved data

Saved profiles contain only an opaque ID, label, SSH target, explicit remote session, and enabled state. Herdr does not store passwords, private keys, agent tickets, or SSH control sockets in the catalog. Authentication stays with OpenSSH.

Herdr separately remembers each machine's remote OS and resolved executable path so repeated `--machine` commands can skip discovery. Existing profiles learn missing information on first use. This cache is optional: missing, invalid, or unwritable cache files do not prevent commands from working. Commands still check live server compatibility. If a cached executable is missing or no longer supports API forwarding, Herdr rediscovers it during the initial read-only check; it never automatically repeats a command that may already have changed remote state.

The client and server negotiate compatibility rather than requiring identical versions. Saved-machine connections additionally need the server's `surface_interest` and `health_check` capabilities. Older servers without those capabilities show Attention until explicitly updated, even if a standalone attach works. Other missing server methods disable only their corresponding actions.

Updating a compatible client does not replace the running remote server or stop its agents. When you need new server-side behavior, update that server explicitly. Normal replacement asks before stopping the server and its pane processes.

Live handoff is experimental and opt-in. For a supported server that needs replacement during standalone setup, you can explicitly add `--handoff` to `herdr --remote`; it is not needed for normal connections or authentication fixes. See [Update](/docs/install/#update) for restart and handoff choices, and [Session state and restore](/docs/session-state/) for what survives each operation.
