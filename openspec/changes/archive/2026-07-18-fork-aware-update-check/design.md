## Context

Herdr's update path lives in two places that both hardcode upstream's hosted manifest URLs:

- `src/update.rs` — the local self-update check (`herdr update`, background `version_check`). Constants `STABLE_UPDATE_MANIFEST_URL` / `PREVIEW_UPDATE_MANIFEST_URL` (previously `https://herdr.dev/{latest,preview}.json`), fetched by `fetch_stable_manifest` / `fetch_preview_manifest`, with channel selection via `UpdateChannel::configured()` reading `[update].channel`.
- `src/remote/unix.rs` — the `herdr --remote` binary-provisioning path, which fetches the same two manifests to decide whether to install/replace a remote helper binary.

A third, separate constant — `DEFAULT_CATALOG_URL` in `src/detect/manifest_update.rs` — points at `herdr.dev/agent-detection/index.toml`. That is the agent-detection manifest catalog, not a release manifest; it is out of scope here.

The fork checks `website/latest.json` and `website/preview.json` into the repo. `preview.json` is regenerated by the fork's `preview.yml` / `scripts/preview.py`. `latest.json` was historically produced by an upstream `update-latest-json` release job that the fork **removed** (it needed upstream deploy keys and published to `herdr.dev`), leaving the committed `latest.json` frozen at whatever upstream snapshot was last synced.

Boundary guardrail: the manifest URL is shared runtime/distribution behavior. It is named neutrally (an update manifest source), carries no UI-surface naming, and adds no server state or socket message.

## Goals / Non-Goals

**Goals:**
- Make every release-manifest fetch on the fork resolve to a manifest the fork **owns and can edit**, so `version_check` and `herdr update` are fork-correct rather than pointing users at upstream binaries.
- Do it with zero hosting: serve the already-checked-in manifests over raw GitHub.
- Keep the local and remote update paths consistent (same two URLs).
- Keep `version_check` on by default.

**Non-Goals:**
- Standing up a fork website, CDN, or `herdr.dev`-equivalent host.
- Changing the manifest JSON schema or the update/compare logic.
- Changing the agent-detection catalog (stays upstream).
- Changing upstream's infrastructure.

## Decisions

### Decision 1: Serve manifests from raw GitHub, not a hosted site

Point the stable/preview URLs at `https://raw.githubusercontent.com/colangelo/herdr/master/website/{latest,preview}.json`. Rationale: those files already exist in the repo, the fork fully controls them, and raw GitHub needs no deploy keys, secrets, or hosting. The alternative — standing up a fork website to mirror `herdr.dev` — is far more infrastructure than a personal fork warrants.

Trade-off: raw GitHub is not a CDN and is best-effort cached; for a personal-fork update check that runs occasionally, that is acceptable.

### Decision 2: Keep the agent-detection catalog on upstream

`DEFAULT_CATALOG_URL` stays on `herdr.dev/agent-detection/index.toml`. The fork does not maintain a manifest catalog, and agent-detection manifests are independent of release self-update. Repointing it would break agent-detection updates with nothing to serve in their place.

### Decision 3: The fork publishes fork data into latest.json

Repointing the URL is necessary but not sufficient: the committed `website/latest.json` held the **upstream** 0.7.4 snapshot (upstream version, protocol 16, `ogulcancelik/herdr` asset URLs). With the URL repointed and `version_check` on, a fork stable user would still have been compared against — and offered — upstream binaries, just served from the fork's own file.

Fix, implemented in two parts:

1. **Publish step:** a fork-owned `update-latest-json` job in `release.yml` runs after `release`, regenerates `website/latest.json` from the fork's own GitHub release, and commits it to `master` (default `GITHUB_TOKEN`) so raw GitHub serves current fork data. It reuses `scripts/changelog.py sync-latest-json` with two additive flags — `--tag` (read the fork's `vX.Y.Z-ac` release while keeping the manifest `version` at the base semver the binary reports) and `--force` (allow base-version reuse across `-ac.N` hotfixes and overwrite an interim-seeded file). This re-introduces a fork-owned equivalent of the removed `update-latest-json` job — pointed at the fork, not upstream — reversing the earlier "no self-update; homebrew-only" decision.
2. **Interim seed:** `website/latest.json` was regenerated now from the real latest fork release `v0.7.1-ac` (base version `0.7.1`, protocol 15, `colangelo/herdr` assets, fork notes, clean single-entry archive). So the repointed manifest is fork-correct and safe immediately — no fork user (current `0.7.4` build or older `0.7.1-ac` build) is offered an upstream binary — rather than only after the next release.

The release job itself cannot be validated without cutting a release, so its end-to-end verification stays manual (tasks 3.2–3.5).

### Decision 4: Keep both update paths in lockstep

`src/update.rs` and `src/remote/unix.rs` each carry their own copy of the two constants (existing structure). Both are updated together and a comment in `remote/unix.rs` points at `update.rs` as the source of truth to keep them from drifting on future syncs.

## Risks / Open Questions

- **Stale-data window (resolved):** the interim seed (Decision 3, part 2) removes the window for the stable manifest — `website/latest.json` carries fork data now, not on the next release.
- **preview.json asset URLs:** the committed `preview.json` still shows `ogulcancelik` asset URLs because `preview.yml` invoked `preview.py` without `--repo`, defaulting to upstream. Fixed by passing `--repo ${{ github.repository }}`; the committed file regenerates with fork URLs on the next preview run (the preview channel is opt-in and rolling, so it is not seeded here).
- **Windows install guidance:** `src/update.rs` still references `herdr.dev/install.ps1` in Windows update guidance text. That is the upstream installer and a separate fork-distribution concern from the manifest URL; out of scope for this change.
